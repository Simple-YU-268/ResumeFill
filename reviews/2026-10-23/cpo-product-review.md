## 2. 新发现的问题（本轮增量）

1. **版本叙述再次滑坡**：package.json 已是 0.25.2，CHANGELOG 停在 0.25.0，0.25.1/0.25.2 有版本说明但未进 CHANGELOG，0.25.2 之上还有两个未归版的 Moka 修复。AGENTS.md 要求"版本号在发布说明中保持一致"——发布说明存在但索引断档，用户和审核者看到的最新叙述落后两个补丁。
2. **统计仪表板有一个哑计数器**：`learned` 在采集但桌面 UI 未展示；且 `learned` 缺分母（学习运行次数），算不出"学习采纳率"——上轮 P3 判定线里明确要看的指标，现在只能看一半。

### 发行判定线（P0a 要落成文字的核心内容）

0.25.x 转正式版的全部条件：① `npm run release:check` 全绿；② 真实页面最小复测通过或失败项经裁决声明为已知限制；③ 版本号五处一致 + CHANGELOG 补齐；④ PRIVACY-REVIEW 日期与版本对齐（已满足）。**没有第四条路叫"再等等"。**

## 4. 发布回看机制设计（仪表板 → 制度的转化方案）

现有资产：五个纯计数器 + 桌面快照存储 + 零遥测的隐私承诺。制度化只差三步：

1. **基线快照**：每次正式发行时，在版本说明里记录开发者本机的计数器快照（scans / fillRuns / verified/attempted / learned 采纳率）作为基线。这是唯一合法的数据源——本机优先定位下，发布回看的主体是开发者自己。
2. **回看日规则**：正式发行后 **14 天或累计 20 次 fillRuns（先到为准）**，对照基线回答三个问题：填写一次通过率是否下降超过 5pp（下降 = 某适配改动伤了通用性）；学习采纳率是否上升（不升 = 学习闭环的复利故事存疑）；fillRuns/scans 是否过低（过低 = 核对环节在流失用户）。
3. **用户样本通道（P2 的导出按钮）**：用户自愿导出纯计数 JSON 附到 issue/反馈。预设判定线：即使只有个位数用户回传，verified/attempted 低于 60% 即触发对应站点适配的复审。

**被证伪就执行的预案**：若正式发行后回看显示一次通过率显著低于开发自测，第一个怀疑对象是 0.24.1 版本戳阻断机制在真实环境误伤——当初为它推迟的是旧脚本兼容路径，回头捡起来。

## 5. 不做清单（更新）

- **不做自动提交/验证码/附件代传** —— 定位红线，代码层强制。复审条件：无。
- **不做云同步/账号/遥测** —— 摧毁唯一信任状。复审条件：定位本身改变。统计导出走用户自愿动作，不开后台通道。
- **不做通用任意网站自动填写承诺** —— 维持"明确适配 + 人工核对"路线。
- **暂缓代码签名** —— 理由：商店上架若跑通，扩展安装不再依赖安装包信任链；证书费用花在商店渠道已覆盖的分发上回报递减。复审条件：商店被驳回且短期无法上架，或 issues 中 SmartScreen 拦截反馈集中出现。
- **暂缓 popup autoAI 改默认不勾** —— 理由：resolution 已记录"主动参与是用户明确要求"，且未配置模型时无实际请求。复审条件：商店审核对"默认勾选 AI"提出权限质疑，或走廊测试显示新用户因此误以为数据默认外发。

---

**收尾一句话**：这个产品现在最缺的不是任何代码，而是**三次对外动作**——一次真实页面复测、一次商店提审、一次正式发行。它们都不难，难的是承认"等条件齐全"已经等了三个版本。把 P0a 的判定线写成文字，下一次评审只问一个问题：线到了没有。
