# 发行判定线（Release Gate）

本文件定义「开发测试版」转为「正式发行版」的全部条件。目的：把「再等等」变成可裁决的决定。任何一条不满足即不发行；**没有第四条路叫「再等等」**。

## 转正式版的必要条件

1. **门禁全绿**：`npm run release:check` 通过（版本五处一致 + CHANGELOG 含当前版本条目 + 版本说明存在 + PRIVACY-REVIEW 已审到当前版本 + 网关版本跟随包版本）；`npm test`、`npm run test:browser`、`npm run test:desktop` 全绿；`npm run privacy:artifacts` 在构建产物上零发现。
2. **真实页面最小复测**：在至少 1 个真实报考/招聘页面（Moka 或目标报考站）跑通最小协议——只读扫描、合成资料填写、回读核对、不提交；版本戳无误报；Layui/sd-Select 控件不误判。失败项必须逐一裁决：阻断发行，或在版本说明中声明为已知限制后发行。
3. **Live AI 验证保鲜**：`dist/ai-live-verification.json` 由当前发行代码跑出（脚本 sha256 与 productVersion 打标一致），`valuesSent:false` 不变。证据必须与发行代码同版，不得以「上次跑过」替代。
4. **隐私审查对齐**：PRIVACY-REVIEW.md 的 `Reviewed for v<version>` 日期与发行版本一致（已由门禁强制）。

## 发行后回看规则

正式发行后 **14 天或本机累计 20 次 fillRuns（先到为准）**，对照发行时记录的基线计数器快照回答三个问题：

- 填写一次通过率（verified/attempted）是否下降超过 5 个百分点？下降 → 怀疑最近适配改动伤了通用性，复审对应适配。
- 学习采纳率是否上升？不升 → 学习闭环的复利故事存疑，复审学习入口可见性。
- fillRuns/scans 是否过低？过低 → 核对环节在流失用户，复审核对屏摩擦。

若一次通过率显著低于开发自测，第一怀疑对象是版本戳阻断机制在真实环境误伤，优先复查。

## 用户样本通道

用户可自愿从桌面端导出纯计数统计摘要（不含标签、路径、网址与任何值）附到 issue。预设判定线：即使只有个位数用户回传，verified/attempted 低于 60% 即触发对应站点适配的复审。
